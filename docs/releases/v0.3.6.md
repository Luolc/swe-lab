# v0.3.6 — 2026-09-06

Three PRs since v0.3.5 (#442, #443, #444), and two of them reach a consumer.
One is an **ABC that grew a method**, so a downstream `Store` subclass stops
instantiating until it implements it; the other **removes a section from the
judge's user prompt**, so a judge prompt built on this version is not the one
0.3.5 built from the same observation. Everything else here is additive: the
whole pipeline as one workflow, its 2×2 reading as a subcommand, a persisted
verdict artifact, and three new columns on the supervisor's decision rows.

This release is numbered `0.3.6`. Which digit a swe-lab release moves is not
inferred from what changed — it is fixed by
[`conventions.md` → Which digit moves](../conventions.md#which-digit-moves).

Raw commit list: the GitHub Release's generated notes.

## Breaking

### 1. `Store.delete(key)` is a new abstract method (#442, [ADR-0023](../decisions/ADR-0023-phase-a-returns-as-an-entry-of-the-from-scratch-chain.md) §6)

**What changed.** `swe_lab.sandbox.store.Store` is an ABC, and it gained

```python
@abstractmethod
def delete(self, key: str) -> None: ...
```

**A `Store` subclass that does not implement it no longer instantiates** —
`TypeError: Can't instantiate abstract class … with abstract method delete`,
raised at construction, before anything runs. The two stores in this repo
(`FilesystemStore`, and `FakeStore` in `swe_lab.sandbox.testing`) implement it;
a subclass living in your code does not.

**Why.** The workflow runner needs to retire the previous invocation's
`workflow.json` before the new one starts (§3 below), and the store is the only
thing that can remove an object. It is an abstract method rather than a default
that raises, because a store which silently cannot delete would leave the
runner's guarantee unenforceable in exactly the store where it matters.

**What you must do.** Implement it, with **idempotent** semantics: *a key that
is not there is not an error.* That is the contract the one caller relies on —
it cannot know whether a previous invocation left a record, and "nothing to
remove" is the ordinary first-run case.

```python
class MyStore(Store):
  @override
  def delete(self, key: str) -> None:
    """Remove the object at `key` if it is there; absent is not an error."""
    self._path(key).unlink(missing_ok=True)   # FilesystemStore's own body
```

For an object store with no missing-ok flag, swallow the not-found error and
let every other failure through — do not make `delete` a blanket `try/except`.

This one **raises**, loudly and immediately, so there is no silent-wrong-thing
window: if your store constructs, you have implemented it.

### 2. The judge's user prompt loses the `# Prior supervisor interventions` section (#443, [ADR-0024](../decisions/ADR-0024-the-judge-is-not-told-what-the-supervisor-said.md), issue [#381](https://github.com/Luolc/swe-lab/issues/381))

**What changed.** `Observation.said` — the corrections the supervisor has
already delivered in this run — used to be rendered into **both** model calls'
user prompts. It is now rendered into the writer's and **not** the judge's.
The section is **absent from the judge's prompt, not empty**: no heading, no
`(nothing yet)` placeholder, nothing.

`swe_lab.trace_synthesis.judge.supervising_policy` gained
`said_visibility: SaidVisibility` (`Literal["writer", "both", "none"]`),
defaulting to `"writer"`:

| `said_visibility` | judge's prompt | writer's prompt |
|---|---|---|
| `"writer"` (default, new) | section absent | section rendered |
| `"both"` | section rendered | section rendered |
| `"none"` | section absent | section absent |

`"both"` restores the pre-0.3.6 prompt: the section returns in the same place,
with the same heading and the same body, and the surrounding text is untouched
— so a prompt built under `"both"` is byte-identical to 0.3.5's. (That is read
off the builder's diff; what a named test pins is that the section is present
under `"both"` and absent under `"writer"` / `"none"` —
`test_the_judge_prompt_does_not_depend_on_what_was_said`.)

The shipped workflow definitions all name `"writer"`, through one constant,
`SUPERVISOR_SAID_VISIBILITY` in `swe_lab.workflow.definitions`. It is **never
read from the environment**, deliberately: an arm whose setting the record
cannot show is not an arm.

If you pass your own `prompt_builder=` to `supervising_policy`, it is handed to
both calls as-is and owns this question itself — `said_visibility` does not
reach it, though it is still recorded on the policy (and so on every decision
row) as the mode the default builders would have used. The switch on the
builder is `SupervisorPromptBuilder(include_said=...)`.

**Why.** Issue #381 replayed the shipped supervisor over one recorded event
stream with the judge's evidence, model and criterion held fixed, so that the
`said` section was the only difference between a speaking arm and a silent one.
The judge's `off_track` rate after the first correction was **104/134** in the
speaking arm against **2/159** in the control — the judge was reading the
supervisor's own corrections as the actor's record and confirming itself for
the rest of the run. ADR-0024 has the full table; the owner ruled on it on
2026-09-06 after a three-party debate.

**What you must do.** Nothing raises here, and nothing is logged as a version
change — this is the quiet kind.

- **Pinned judge-prompt hashes, golden prompts, or recorded request fixtures**
  will not match. Re-pin them, or set `said_visibility="both"` to keep the old
  bytes.
- **Comparing supervision runs across this boundary**: don't. A run on either
  side was judged from a different prompt, so treat them as two configurations
  rather than two samples, and re-baseline. Every decision row now records
  `said_visibility` and `judge_prompt_sha256` (§8 below), which is how you can
  tell after the fact which shape a row was produced under.
- **A custom `prompt_builder`** keeps doing exactly what it did; it was never
  affected by this default. If you want the new behavior in one, pass
  `include_said=False` (the `SupervisorPromptBuilder` default is now `False`).

**What this does to a whole run is not measured here.** The #381 numbers are a
replay over one recorded stream, not a solve-rate result; this note does not
predict an intervention rate or a cost from them.

## Behavior changes

### 3. The workflow runner removes the previous invocation's `workflow.json` before it starts (#442, [ADR-0023](../decisions/ADR-0023-phase-a-returns-as-an-entry-of-the-from-scratch-chain.md) §6)

**What changed.** `Workflow.execute` now deletes the run's workflow record —
`<sweep>/<instance>/r<rollout>/workflow.json` — **before the first entry runs**,
and writes the new one **last**, as it always did. On every invocation, resumes
included: a resumed run that re-runs a failed entry and dies mid-way would
otherwise leave the same stale record behind.

**The property you gain:** *a record that is present is the current
invocation's.* Before, a killed re-run left the previous run's record sitting
in place beside fresh shards, and nothing on either could tell you so — the
clock has one-second grain, and a re-run can rewrite a shard's artifacts
without moving the metrics the record copies. ADR-0023 §6 records both
read-side rules that were tried and retired.

**The cost:** while a run is in flight there is **no record at all**. A run
killed anywhere between its first shard and its record now leaves shards and no
`workflow.json`, where 0.3.5 would have left the previous invocation's.

**Only that one roll-up is removed.** Per-task shards (`run.json`) and terminal
markers are untouched, and **resume still works exactly as before** — it reads
task markers and never reads a workflow record.

**What you must do.** If you have a reader that treats "a `workflow.json` is
here" as "this run finished at some point", it now means something stricter and
more useful. If you have one that treats its absence as "this run never got
past binding" (ADR-0009's wording), widen that to **"the latest invocation
never finished"** — either it never got past binding, or it retired the
previous record, ran, and died. Polling for a record mid-run will now find
nothing where it used to find a stale one.

## Added

Nothing here is a break; each is a new name or a new file beside the existing
ones.

### 4. Every grading entry persists `unit_test.verdict.json` (#442, [ADR-0023](../decisions/ADR-0023-phase-a-returns-as-an-entry-of-the-from-scratch-chain.md) §5)

`Verdict` gained a concrete `facts()` on the ABC — `resolved`, `score`,
`metrics()`, `summary()` — and the unit-test observer now contributes it as an
inline artifact named `unit_test.verdict.json`, on **every** grading entry:
`unit_test`, `gold_unit_test`, every `*_and_unit_test` chain. It is written
whatever the script did, since grading runs in `before_destroy` regardless.

**This is an additive artifact and not a report-contract change** — worth
saying plainly, because "the grader writes a new file" reads like one. The
`AttemptRecord` schema, the workflow record, the CLI summary and
`swe_lab.reporting` are all untouched; one more name appears in an attempt's
`artifact_keys`.

It exists so the failure can travel a workflow edge: the metrics carry only
scalars, and a consumer that needs to know *which* tests failed — the Oracle,
briefing itself — had nothing else to read.

### 5. New workflow: `from_scratch_guided_trace` (#442, [ADR-0023](../decisions/ADR-0023-phase-a-returns-as-an-entry-of-the-from-scratch-chain.md))

The whole pipeline from nothing, over a plain instance — no `oracle_failures`
row to prepare first:

```sh
python -m swe_lab run from_scratch_guided_trace <instance_id> --persist --sweep <id>
```

Five entries: blind rollout → blind grading → Oracle analysis → guidebook-
supervised segmented rollout → guided grading. They run under five distinct
keys — `baseline_rollout`, `baseline_unit_test`, `oracle_analysis`,
`guided_rollout`, `guided_unit_test` — and **the key is the whole namespacing
scheme**: it is the task segment of every store key, so the two rollouts' and
the two gradings' identically-named artifacts (`patch.diff` and friends) cannot
collide, and the workflow layer refuses a repeated key outright.

**It is unconditional.** An instance the blind rollout already solves still
gets its Oracle analysis and its guided arm — the reading this chain exists for
is a 2×2, and a chain that stopped early could never fill the cell where the
guidebook made things *worse*.

The Oracle takes the failure over edges, under the producers' own names
(`conversation.json`, `patch.diff`, `patch.base_ref.txt`,
`unit_test.verdict.json`) rather than the `oracle_failures` staging names. The
existing `oracle_analysis` and `oracle_guided_trace` workflows are unchanged
and still start at phase B over an `oracle_failures` record.

### 6. New subcommand: `swe-lab guided-gain <sweep>` (#442)

```sh
python -m swe_lab guided-gain <sweep-id> [--store-root <dir>]
```

The 2×2 reading of a `from_scratch_guided_trace` sweep — `kept`, `gained`,
`regressed`, `unsolved` — plus the two marginals (solved at baseline, gained
with the guidebook) and an explicit **incomplete** count. JSON on stdout, a
table on stderr, so the numbers pipe while a person still sees them.

Both verdicts of a pair are read off the run's **workflow record**, never off
whichever attempt shard has the highest number (which a forced re-run can leave
behind from an older run) — which is what §3 above exists to make sound. A run
with no current record, or whose record gives no verdict for a grading key, is
counted as incomplete and named with what it lacks; it is never folded into a
cell. A sweep with no runs at all is refused with exit 1 rather than rendered
as four zeros.

`--baseline-key` / `--guided-key` override the entry keys it reads.

### 7. `OracleAnalysisTask(failure_inputs=...)` (#442)

Where phase B reads the failure from. Default `False` — the instance's own
`oracle_failures` mounts, as before, and the staged mounts stay **byte-
identical**. `True` takes the conversation, verdict, patch and base ref as
declared workflow inputs, under the producers' names, and compiles the grading
procedure against the run's recorded pre-agent baseline. `privileged_mounts`
and `build_oracle_prompt` gained a matching keyword-only `failure=` argument
(defaulting to the staged names), so existing calls are unaffected.

### 8. Three new columns on every supervisor decision row (#443, [ADR-0024](../decisions/ADR-0024-the-judge-is-not-told-what-the-supervisor-said.md))

Both the streaming `Supervisor` and the `SegmentedRun` loop now write, on
**every** row kind (`spoke`, `silent`, `lapse`, `gap`, `unjudged`):

| Field | What it is |
|---|---|
| `said_visibility` | Which mode the row ran under (`"writer"` / `"both"` / `"none"`), or `null` for a policy that makes no model call and so has no prompt for the question to apply to |
| `said_count` | How many corrections had been delivered **before** this boundary — so a `spoke` row does not count its own |
| `judge_prompt_sha256` | SHA-256 of the judge's user prompt, on rows that carry a `judge_input` |

Together they are how a row recorded under either shape of §2 can be told apart
after the fact, and how a row can be paired with its counterpart in another arm:
two rows with one `judge_prompt_sha256` were judged on the same bytes. Read them
with a default, as always — a row written by 0.3.5 has none of the three.

### 9. A judge transport failure records what was asked (#443, [ADR-0024](../decisions/ADR-0024-the-judge-is-not-told-what-the-supervisor-said.md))

New `swe_lab.trace_synthesis.judge.JudgeTransportError`, raised when the
judge's transport raises before any answer comes back. It carries the
credential-free request payload as `judge_input`, which travels out through
`PolicyLapseError` (new `judge_input` attribute) onto the decision row — so a
boundary whose judge call died records `judge_input` and its
`judge_prompt_sha256` instead of an empty row. `JudgeAnswerError` now carries
the same field for the answer-came-back-unusable case. Never retried, for the
reason the answer-shape error is not: a second ask would make the verdict a
function of how many times we asked.

**One thing to react to, if you catch transport exceptions by type:** a
transport exception raised inside `ModelJudge.__call__` no longer propagates as
itself — it is wrapped in `JudgeTransportError` (a `RuntimeError`), with the
original as `__cause__`. Code catching a specific client exception *around* a
judge call must catch `JudgeTransportError` (or read `__cause__`) instead.
Nothing in this repo does: `SpeakWhenOffTrack` already caught broadly and
converted to a `PolicyLapseError`, which is unchanged. *(This item's wrapping
consequence is the release author's reading of the diff, not part of the
implementing PR's own description.)*
